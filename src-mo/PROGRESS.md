### 一条重要约束

**`src/compiler.mo` 只能使用 seed 支持的语法子集。**

seed 是手写汇编写的引导编译器，它不支持一元 `&`、数组、结构体、import。
compiler.mo 里只用二元 `&`（按位与），从不写 `&x`。

这不是限制，是刻意的：它保证 seed 永远能引导，自举链条不会断。
代价是编译器源码本身不能用自己最炫的特性——这在自举语言里很常见。

### 实现要点：else if 用迭代，不用递归

递归写法（外层 `parse_if` 里再调 `parse_if`）会为每一层各自分配出口标签，
于是每多一层就多一对 `jmp` + `label`。

改成迭代后，**整条链共用一个出口标签 `end`**，每一轮只有一个「下一分支」标签：

```
jcc  els1      ; 条件 1 不成立则跳到 els1
<块 1>
jmp  end
els1:
jcc  els2      ; 条件 2
<块 2>
jmp  end
els2:
<else 块>
end:
```

关键是 **seed 与 mo 必须用同一种结构**。递归版和迭代版会产出不同的字节，
自举立刻就会报不一致——这也是选择迭代的另一个理由：它更好在汇编里表达。

### 一次痛苦但值得的调试

加 `else if` 之后，seed 突然报 `error: cannot open output`，
并且编出来的编译器一运行就段错误。排查过程：

1. **先确认是谁的问题**：拿"回退掉新特性"的编译器源码给当前 seed 去编，
   产物同样崩溃 → 说明是 **seed 坏了**，不是编译器源码坏了。
2. **加探针定位受影响的内存**：输出文件名变量在解析阶段就被写成了 `480`，
   而 `480` 正好是一个函数帧大小——指向写帧大小的那段代码。
3. **算出写入点地址**，反推是哪个数组越界。
4. **二分输入源码**锁定触发点，最后发现**加一个空函数就能触发**——
   说明是累积越界，不是某个语法结构。
5. 把新增的 `loop_push`/`loop_pop` 改成空操作，问题消失 → 锁定循环标签栈。

**根因**：seed 的 `while` 分支里调用了 `loop_push`（压入循环标签），
却**从来没有配对的 `loop_pop`**。每编译一个 `while` 循环，栈顶就涨一格，
最终越过 `lstk` 的 512 字节边界，写坏了紧邻的输出文件名。

修复只是一行——在 `while` 结尾补上 `call loop_pop`。

### 三条经验

1. **症状离根因可以很远**。表现为"打不开输出文件"，实际是几百 KB 之外
   的循环标签栈越界。不要相信表面症状。
2. **先判定是工具坏了还是输入坏了**。用"回退版源码 + 当前编译器"
   这一组对照实验，一锤定音。
3. **seed 里 `lstk` 这类新增全局缓冲，必须有配对的压栈/弹栈**。
   手写汇编没有作用域和 RAII 保护，漏一次弹栈就是几十 KB 之外的随机破坏。

已把第 3 条写进 `CONTRIBUTING.md`。

**byte 数组与后续 i64 变量栈帧重叠** —— 数组占 8 字节却没对齐，

字符串只能声明成 `i64`，而 `i64` 不能下标，会被类型检查拦下。

### set_pos 为什么能安全回退

判断常量下标要试探性地多读一个 token，然后退回去走正常路径。
`set_pos` 会把 `LINE`/`COL` 重置为 1 再重算，
所以回退后行列信息依然正确——否则后续报错的行列号会整体偏移。

### 一个诚实的限制

`a[0 - 1]` 编译期拦不住：`-1` 是 `-` 和 `1` 两个 token，
不满足"整数 token 紧跟 `]`"。运行时仍会被无符号比较拦下，不会漏。
要覆盖它需要常量折叠，而那依赖中间表示。

### 设计上做对的一件事

复合赋值**复用二元运算的 `g_*` 函数**，而不是另写一套：

```
load_sym(x); g_push_rax(); parse_expr(); g_pop_rcx(); g_add(); store_sym(x)
```

好处是语义与 `x = x OP e` 天然一致——`g_sub` 算 `rcx - rax`（左减右），
`g_idiv` 算 `左 / 右`，直接复用就不会把方向搞反。
测试 `50_compound_sub` 专门盯这一点（10 -= 5 得 5，不是 -5）。

### seed 侧失败，以及撤销时的二次事故

想在 seed 里也实现一遍以保持一致。词法改好了，反汇编确认 `+=` 被正确识别；
但 `parse_stmt` 的复合分支始终报 `syntax error`。

探针打出来的事实是：**分派前每一步都对**——
tokbuf 是 `+=`、tok_kind 是 4、`compound_op` 返回 1、`sym_lookup` 找到符号——
但分支内部没执行到底。

继续定位的代价超过收益，于是撤销 seed 侧全部改动。

**撤销脚本本身又闯了祸**：用 `s.index('    call next_token\n')` 定位，
匹配到的是文件里**第一个**（在 `parse_program` 里），不是 `parse_stmt` 里的那个，
结果整段删掉了两者之间的内容，连 `parse_block` 一起没了，`ld` 报 undefined reference。

最后靠 **0.6.0 的打包快照整体覆盖**才恢复。

两条教训：

1. **按内容定位时要确认匹配唯一**，否则等于闭着眼睛下刀。
2. **打包快照要保留**——这次它真正救了场。

### 一个刻意的取舍

seed 不支持复合赋值，意味着 `src/compiler.mo` **不能**用 `+=`。

这不是疏漏：seed 本就不支持数组、结构体、`import`、字符字面量。
它只负责把 `compiler.mo` 编出来，用不到的语法就不实现。

代价是墨语言的编译器源码不能用自己最方便的语法。
这在自举语言里很常见。

## 阶段十七 · 0.12.0：栈顶缓存（2026-10-08）

第一个真正意义上的寄存器分配（一个寄存器）。
二元运算的左操作数放 `rbx` 而不是压栈，省一对内存访问。

### 不变式

`rbx` 里是「最后一次 push」的值。任何新的 push 之前先 spill，
栈序就天然正确，嵌套表达式与函数调用都不用特殊处理。

### 三个踩坑

1. **spill 必须放在「回退字节」之后**。折叠路径要回退刚发的常量加载，
   若先 spill 再回退，回退掉的是 `push rbx` + 常量加载的后半段，
   指令直接错位（25 个测试当场段错误）。
2. **跨函数调用会泄漏**。被调函数里的 push 会 spill 调用者缓存在 rbx 的值，
   把它压进被调函数的栈帧，返回后取回的是错的。调用前必须先 spill。
3. **seed 里 `call emit1` 会破坏 `%r8`**，而 `lastv` 就存在 r8 里。
   把 spill 插在 `subq`（回退）之后、比较之前，判断就用了被冲掉的值。
   改到比较之后才对。

### 一个隐患，已修

除法用 rbx 当除数。最初只在 mo 侧加了 spill，seed 侧没加，
两侧在未被测到的路径上不一致 —— 但自举仍然通过，
因为 `compiler.mo` 恰好没有触发该场景。
**自举只能证明「被测到的路径一致」，不能证明实现等价。**
两侧都已补上。

| 基准 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| array | 105 ms | 90 ms | -14% |
| str | 24 ms | 16 ms | -33% |
| loop | 188 ms | 166 ms | -12% |
| sort | 15 ms | 14 ms | -7% |

### 然后做了期 19 的主要内容：容器库

`lib/vec.mo`，动态数组。设计上最关键的一点：

> 句柄 = 固定大小的头部（数据指针 + 长度 + 容量）。
> 扩容时只重分配数据区，头部地址不变。
> 于是句柄可以随便传，不需要 realloc 那种"返回新指针"。

代价：扩容丢弃旧数据区（bump 分配器不回收），空间上浪费。

### 用真实程序验证，而不是只跑单元测试

`examples/freq.mo` 改用 vec，去掉了"最多 200 词 / 每词 24 字节"的上限。
实测 3000 词文本统计出 **400 个不同单词**——旧版会在 200 处静默截断。

这就是容器库的价值：**它消除的是"静默截断"，不是"报错"**。
程序旧版照样能跑、照样返回 0，只是结果不完整。

## 阶段二十一 · 1.2.0：map + 未使用变量检查（2026-10-08）

### map

`lib/map.mo`：开链法 + FNV-1a，负载因子 > 1 翻倍。

**一个刻意的决定：键在插入时拷进堆里**，而不是存调用方的指针。
早期容器几乎都栽在"存了别人的指针"上——调用方复用缓冲区后，
表里的键就全变了。测试里专门覆盖这条：

```mo
let k: i64 = alloc(32);
strcpy(k, "k1"); map_put(m, k, 100);
strcpy(k, "k2"); map_put(m, k, 200);
# k1 必须还是 100 —— 如果存指针，这里会是 200
```

### 踩坑：节点字段偏移写错一格

`mk_node` 布局是 `next(+0) hash(+8) key(+16) val(+24)`，
但 `node_of` 里读成了 `+16` / `+24`。
测试 `map_get(m, "apple")` 返回 0 才暴露。

这类 bug 值得记：**结构体字段靠"我记得是第几个"来写，迟早错一格。**
测试才是指标。

### 未使用变量检查

```
test.mo: warning: unused variable 'b'
```

选**警告**而不是错误，两个理由：
1. 它不该挡住编译
2. 万一误报，代价只是多打几行字，不是编译不过

只在 moc 实现，seed 不实现——它不影响输出字节。

## 阶段二十二 · 寄存器分配：**未完成**

### 结论

**当前架构做不了。** 编译器没有 IR（实测 `AST`/`IR` 相关标识符 0 次），
边解析边发射。寄存器分配需要变量的活跃区间，
那要看完整个函数体才算得出来。

前六项优化能落地，正是因为它们只动最后一条指令、不需要跨语句信息。
寄存器分配需要，所以绕不开。

### 试过的折中：多寄存器栈顶缓存

想把栈顶缓存从 1 个寄存器扩到多个。**实测没用**：

函数调用的实参确实是连续 push 的，但它们最终要 pop 到
**特定寄存器**（第 1 个 rdi、第 2 个 rsi……）。
缓存多一层只是把"内存→rdi"变成"rbx→内存→rdi"，多绕一步。

参照数据：`fib` 基准在栈顶缓存后是 **0% 提升**——
它几乎全是函数调用，印证了这个判断。

### 方案

期 22 拆成 22a（IR 重构）+ 22b（线性扫描分配）。
**22a 没做完，22b 无从下手。**

22a 的关键在第 3 步：生成 IR + 把当前栈式逻辑原样搬成后端，
然后**验证自举产物与重构前逐字节相同**。
这一步不改变任何输出，是纯粹的结构准备，也是安全阀。

详见 `docs/regalloc_design.md`。

### 为什么没有一次性做掉

IR 重构是自举以来最大的一次结构改动。一次性做完风险太高，
而且"边改边看"在自举约束下代价很大——不一致就得二分回滚。
分小步、每步跑自举回归，才是稳的。
