# 数组越界检查

状态：已实现（默认开启）；0.6.0 起常量下标在编译期拦截
日期：2026-10-08（0.6.0 更新）

## 1. 为什么需要

之前墨语言的数组访问**完全不检查**：

```mo
let a: [4] i64 = 0;
a[100] = 1;        # 静默写到数组之外
```

后果是随机的内存破坏——可能什么都不发生，可能踩坏别的变量，
也可能段错误。这类 bug 在真实程序里极难排查。

现在会拦下：

```
mo: index out of bounds
```

并以退出码 1 结束（不是段错误的 139）。

## 2. 实现：一条 cmp 同时管上下界

检查代码只有两条指令：

```asm
48 3D <imm32>     cmp rax, n        6 字节
0F 83 <rel32>     jae panic         6 字节
```

关键在于**用无符号比较**：

- 下标 `>= n` → `jae` 跳转 → panic
- 下标是负数，比如 `-1` → 作为无符号是 `0xFFFF...FFFF`，必然 `>= n` → panic

于是一条 `cmp` + 一条 `jae` 就同时拦住了负下标与上界，
不需要分别判断 `< 0` 和 `>= n`。

第二个关键点：`cmp` **不破坏 rax**，所以下标值还能继续用于
后面的地址计算，不需要额外保存/恢复。

### 检查点不内联

panic 处理例程放在**代码段末尾**，所有检查点跳转到同一处：

```asm
mov rax, 1            ; write
mov rdi, 2            ; stderr
movabs rsi, <msg>
mov rdx, 24
syscall
mov rax, 60           ; exit
mov rdi, 1
syscall
```

如果每个检查点都内联这段代码，一次数组访问就要多 60 字节；
共享一个例程后只多 12 字节。

## 3. 哪些情况会检查

| 情况 | 是否检查 | 原因 |
|---|---|---|
| `a[i]`，`a` 是数组 | ✅ | 编译期知道元素个数 |
| `a[i]`，`a` 是全局数组 | ✅ | 同上 |
| `p[i]`，`p` 是指针参数 | ❌ | 指针不带长度信息 |
| `&a + i*8` 指针算术 | ❌ | 编译器看不出这是数组访问 |

**只对编译期已知长度的数组做检查。** 这是目前最重要的限制。

实测开销（代码段字节数）：

| 程序 | 无检查 | 有检查 | 增加 |
|---|---|---|---|
| `bubble_sort.mo` | 792 | 876 | **+10.6%** |
| `wc.mo` | 4815 | 4815 | 0% |
| `grep.mo` | 5054 | 5054 | 0% |
| `sort.mo` | 5198 | 5198 | 0% |

后面三个是 0%，因为它们处理字符串时用的全是
`load8(s + i)` 这种指针算术，不走下标语法。

这不是疏漏，而是当前语言形态决定的：墨语言只有 `i64` 一种机器类型，
字符串只能按字节用 `load8`/`store8` 访问，没法写成 `s[i]`。

## 4. 踩坑：seed 的字符字面量一直是错的

写 panic 消息时用了字符字面量：

```mo
dbyte('m'); dbyte('o'); dbyte(':'); ...
```

结果程序输出了一串 `'`（39）——每个字节都写成了单引号的编码。

根因在 **seed 汇编的 `lex_char`**：

```asm
.Lch_done:
    incq %r8
    movb (%r10,%r8), %al      # 读闭合引号 —— 把 %al 里的字符值冲掉了！
    cmpb $39, %al
    ...
    andq $255, %rax
    movq %rax, tok_ival(%rip) # 存的是闭合引号的 39，不是 'm' 的 109
```

判断闭合引号时直接往 `%al` 里读了一个字节，把刚解析出来的字符值覆盖了。

修法是用**另一个寄存器**看闭合引号：

```asm
movb (%r10,%r8), %r11b        # 不动 %rax
cmpb $39, %r11b
```

### 为什么之前没暴露

`src/compiler.mo` 里此前没有任何字符字面量——它只能用 seed 支持的语法子集，
而字符字面量一直是"能用但没人用"的状态。测试 `32_char_lit.mo` 是
用 `moc` 编的，moc 的 `lex_char` 用局部变量保存字符值，是正确的。

**只有 seed 那一侧是错的**，而 seed 只负责编译 `compiler.mo`——
直到我在 `compiler.mo` 里写下第一个字符字面量，它才发作。

这条再次印证：**两侧实现必须逐字节一致**。
任何一侧的偏差，都会在某个你没想到的地方冒出来。

## 5. 编译期常量下标（0.6.0）

运行时检查要等程序跑起来。而 `a[9]` 这种**下标写死**的情况，
编译时就能看出来。0.6.0 起直接拦下：

```
test.mo:3:14: error: index out of bounds: constant index >= array length
        return a[9];
                 ^
```

### 怎么在不退化的前提下判断

难点在于：`index_addr` 是先 `parse_expr()` 再收 `]`，
等到那时已经不知道下标是不是常量了。

做法是**试探性地多读一个 token**：当前 token 是整数时，
记下它的值，多读一个看是不是 `]`；是就说明是常量下标。
确认后（或不需要确认时）用 `set_pos` 退回整数 token 的位置，
再走正常的 `parse_expr()` 路径。

关键点：`set_pos` 会把 `LINE`/`COL` 重置为 1 再重算，
所以回退后行列信息依然正确——否则后续报错的行列号会整体偏移。
这是它能安全回退的原因。

### 顺带省掉运行时检查

编译期既已确认合法，运行时的 `cmp` + `jae` 就是多余的，
每处省 12 字节。

**但实测收益是 0%。** 五个示例程序全部如此——
因为真实代码里常量下标极罕见，下标几乎都是循环变量 `a[i]`。

| 程序 | 无此优化 | 有此优化 | 缩减 |
|---|---|---|---|
| `bubble_sort.mo` | 871 | 871 | 0% |
| `freq.mo` | 6574 | 6574 | 0% |
| `sort.mo` | 5091 | 5091 | 0% |
| `wc.mo` | 4698 | 4698 | 0% |
| `grep.mo` | 4932 | 4932 | 0% |

所以这一步的真正价值是**更早发现错误**，不是体积。
把它记下来，免得以后有人（包括我）以为它能减肥。

### 限制：负常量下标拦不住

`a[0 - 1]` 不会在编译期报错。

原因是词法层面 `-1` 是 `-` 和 `1` **两个 token**（一元负号在
`parse_unary` 里处理），所以 `a[-1]` 不满足"整数 token 紧跟 `]`"
这个判断条件。

要在编译期抓住它，得先有常量折叠——而那需要中间表示，
正是 `docs/codegen_opt.md` 里记的"还没做的优化"第一条。
目前这类情况仍由运行时的无符号比较拦住，不会漏。

## 7. 遗留

| 项 | 说明 |
|---|---|
| 指针不做检查 | 需要引入"胖指针"（指针 + 长度）或单独的长度参数 |
| 没有关闭开关 | 性能敏感场景无法关掉检查 |
| 消息不含下标值与行号 | 只有固定一句话，大型程序里定位仍要靠调试器 |
| ~~常量下标不在编译期报错~~ | ✅ 0.6.0 已支持，`a[9]` 编译期就拦下 |
