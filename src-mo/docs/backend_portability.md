# 后端不是「万年一个」：第二个后端与可移植性

版本 1.6.0（2026-10-08）

先直接回答那个质疑：**后端不是不能加，是可以加的。** 这一轮就加了第二个 ——
C 后端。之前我把「成本高」说成了「做不到」，这个表述不准确。

---

## 一、现在有两个后端

| | x86-64 后端（`moc`） | C 后端（`mo2c`） |
|---|---|---|
| 产物 | ELF64 可执行文件 | C 源码 → 交给 gcc/clang |
| 依赖 | 无（不链接 libc） | 需要一台 C 编译器 |
| 架构 | 仅 x86-64 | x86-64 / ARM64 / RISC-V / 任何有 C 编译器的地方 |
| 系统 | 仅 Linux | Linux / macOS / Android(NDK) / BSD…… |
| 越界检查 | 有（编译期 + 运行时） | **无**（C 不管这个） |
| 速度 | 直接运行机器码 | 取决于 C 编译器 |

用法：

```bash
./bin/moc  prog.mo prog.elf          # 后端 1：直出 ELF
./bin/mo2c prog.mo > prog.c          # 后端 2：翻译成 C
gcc -O2 prog.c -o prog
```

或统一入口：

```bash
./tools/mo.sh build  prog.mo -o prog.elf   # 后端 1
./tools/mo.sh cbuild prog.mo -o prog       # 后端 2
./tools/mo.sh ctest                        # 两个后端结果比对
```

### 为什么 C 后端能解决「多架构」

ARM64 / RISC-V / Android 这些目标，墨语言自己不会生成代码。
但 **C 编译器会**。把墨语言翻译成 C，就相当于把后端工作委托出去 ——
一次投入，白嫖所有现成后端。

代价要写清楚：

1. **不再是零依赖**（需要 gcc/clang）
2. **数组越界不再检查** —— 这是两个后端之间真实的语义差异
3. 生成的是 C 源码，不是机器码

## 二、C 后端当前状态：alpha

### 已验证（自动化测试锁定）

`tools/cbackend_test.sh` 对同一份源码分别用两个后端编译运行，
**退出码必须相同**：

```
cbackend: OK（3 个程序，两个后端结果一致；pending 2 个）
```

覆盖：变量声明、算术与位运算、if/else、while、数组下标读写、
复合赋值、结构体字段赋值、递归。

### 还没支持（单独放在 pending/）

- 函数调用出现在**表达式**里，例如 `return fib(a) + fib(b)`
- 函数调用的实参里再嵌函数调用，例如 `f(g(x))`

这两条也是**原生后端本来就有的坑**（实参嵌套会破坏函数名缓冲），
不是 C 后端独有的问题。修好之后把 pending/ 里的用例移上来即可，
测试自动覆盖。

## 三、硬件访问：能做，但受权限约束

`examples/hwinfo.mo` 实测输出（本机）：

```
[内核]   sysname / release / machine / uptime
[CPU]    AMD EPYC 9K65 192-Core Processor，2250 MHz，2 cores
[内存]   total 2519474176 bytes，available 1856320 kB
[温度/电源]  thermal_zone0 / BAT0（读不到就明说）
[块设备]  / 容量 5117 MB，可用 5103 MB
[PCI]    net: eth0 / lo / ...
[/dev/mem]  需要 root；打不开就明确说明，而不是假装成功
```

路子只有两条，都很朴素：

1. **sysfs / procfs**（`/proc`、`/sys`）—— 普通权限就能读，覆盖绝大多数硬件信息
2. **系统调用**（`uname`、`sysinfo`、`statfs`、`ioctl`）

真正"碰硬件"（`/dev/mem`、`ioperm`）需要 root，
示例在权限不足时**明确提示**，不静默失败 —— 这条原则和越界检查一致。

### depcheck 为什么要单独做

这轮发现一个真实缺陷：**库文件没声明自己的 import**。
平时能编译，是因为主文件恰好 import 了那个库；
但只要有人单独引用它，立刻失败。

`archive.mo` / `dir.mo` / `log.mo` / `pty.mo` / `vec.mo` / `net.mo`
都有这个问题，已全部补上。现在 16 个库文件都能独立引用。

> 测试里很难暴露这类缺陷（因为测试都会 import 一大堆），
> 但它是真实使用时最常见的踩坑方式。

## 五、这轮挖出的编译器问题

### 1. 全局数据超过约 1MB 会静默破坏符号表

写 `mo2c` 时先给了 1.1MB 的缓冲区，编译报 `undefined symbol 'PP'` ——
一个明明声明过的全局变量。

根因：输出数据段缓冲（`O_DATA`）与名字区（`O_NAMES`）只隔 1MB，
程序的全局变量 + 字符串字面量超过它，就覆盖到名字区，符号名被冲掉。

**这是静默破坏**：不报错直接给出错的符号。建议后续加上诊断
（超限就报 "global data too large"，而不是诡异的 undefined symbol）。
当前缓解方式是控制全局变量规模（`mo2c` 已压到 590KB）。

### 2. 全局变量必须先声明后使用

函数可以后定义，但**全局变量不行**。写 `mo2c` 时踩到两次
（`OUTP`、`FP` 声明在使用之后）。

这条没有写进语言参考，是个文档缺口。

### 3. `==` 比 `&` 结合更紧（1.5.0 已修，此处重申）

`(m / 4096) & 15 == 8` 会被解析成 `(m / 4096) & (15 == 8)`。
**务必写 `((m / 4096) & 15) == 8`。**
