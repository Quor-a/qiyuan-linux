# 寄存器分配：为什么现在做不了，以及要做什么

状态：**未实现**。期 22 的主要工作，需要前置重构。
日期：2026-10-08

---

## 1. 结论先行

墨语言当前**没有中间表示**——编译器边解析边发射机器码。
完整的寄存器分配（图着色 / 线性扫描）需要知道每个变量的**活跃区间**，
而活跃区间只有在看到整个函数体之后才算得出来。

所以期 22 要拆成两步：

| 步骤 | 内容 | 风险 |
|---|---|---|
| **22a** | 把代码生成层改成有 IR（至少是函数级） | 高：改动面大，易破坏自举 |
| **22b** | 在 IR 上做寄存器分配 | 中 |

**22a 没做完之前，22b 无从下手。**

## 2. 当前架构是什么样的

`parse_expr` 在解析的同时就把字节发射出去：

```mo
fn parse_add() -> i64 {
    parse_mul();
    while accept("+") == 1 {
        g_push_rax();      # 左操作数入栈（现在优化成 mov rbx, rax）
        parse_mul();       # 右操作数算到 rax
        g_pop_rcx();       # 左操作数回到 rcx
        g_add();
    }
}
```

整个编译器里 `AST` / `IR` 相关标识符出现 **0 次**（实测 grep）。

前六项代码生成优化之所以都能落地，正是因为它们**只动最后一条指令**：

| 优化 | 为什么能绕开 IR |
|---|---|
| 常量加载窄化 | 只改单条指令编码 |
| disp8 寻址 | 只改单条指令编码 |
| push 折叠 | 只改最后一条指令 |
| 右操作数常量化 | 回退并重发最后一条 |
| 2 的幂乘法移位 | 只改单条指令 |
| 死跳转消除 | 回退最后 5 字节 |
| **栈顶缓存（1.0）** | 只缓存"最后一次 push" |

它们的共同点是：**不需要跨越语句的信息**。
寄存器分配需要，所以它绕不开。

## 3. 为什么"多寄存器栈顶缓存"收益有限

一个看起来可行的折中：把栈顶缓存从 1 个寄存器（`rbx`）扩到多个。

**实测发现没用**，原因是函数调用的参数传递：

```mo
fn parse_call() -> i64 {
    while tok_is(")") == 0 {
        parse_expr();
        g_push_rax();      # 连续 push 每个实参
        na = na + 1;
    }
    ...
}
```

多个实参确实是连续 push 的，但它们最终要 `pop` 到**特定寄存器**
（第 1 个进 `rdi`、第 2 个进 `rsi`……）。
也就是说，无论中间缓存在哪个寄存器，最后都得落到 ABI 规定的那个。

缓存多一层，只是把"内存 → rdi"变成"rbx → 内存 → rdi"——**多绕一步**。

所以这条路不通。真正的收益来自"把局部变量常驻寄存器"，
而那正是需要活跃区间分析的部分。

## 4. 22a 要做的事（IR 重构）

### 4.1 最小可行的 IR

不需要 LLVM 那种完整体系，够用就行：

- 函数为单位收集指令序列
- 每条指令有：操作码、若干操作数、结果
- 操作数可以是：常量 / 虚拟寄存器 / 内存槽（局部变量）
- 虚拟寄存器数量不限，由分配器决定最终落到哪

### 4.2 改造路径

1. 先让 `parse_expr` 生成 IR 而不是直接发射字节
2. 保持一个"IR → 字节"的后端，先把当前的栈式逻辑原样搬过去
3. **验证这一步的自举产物与重构前逐字节相同**（关键检查点）
4. 确认无误后，再在 IR 上加优化遍

第 3 步是安全阀：如果字节不一致，说明语义被改了，先修到一致再往下走。

### 4.3 风险与对策

| 风险 | 对策 |
|---|---|
| 改动面大，一次改完容易失控 | 分小步，每步跑自举回归，**不攒批** |
| 新后端与旧行为有细微差异 | 以"逐字节相同"为验收标准，不是"测试通过" |
| seed 侧要不要同步 | 要。影响输出字节的改动两侧必须镜像 |

**最后一条是硬约束**：seed 是手写汇编的引导编译器，
它不实现的东西，`src/compiler.mo` 就不能用。
如果 IR 重构让 `compiler.mo` 用上了新语法，seed 得跟着改。

## 5. 22b 的算法选择

建议**线性扫描**而不是图着色：

- 实现简单得多，单趟即可
- 对直线代码（我们生成的正是这种）效果接近图着色
- 图着色的收益主要体现在寄存器压力大时，而我们的 IR 本来就很直

需要的数据：

- 每个虚拟寄存器的**定义点**与**最后使用点**
- 活跃区间 = [定义点, 最后使用点]
- 按起点排序，扫描时维护"当前活跃集合"，溢出则挑区间最长者落栈

## 6. 已经拿到的收益（1.0 的栈顶缓存）

作为参照，记一下当前的实测数字：

| 基准 | 优化前 | 栈顶缓存后 |
|---|---|---|
| array | 105 ms | 85~90 ms（-15%） |
| str | 24 ms | 16~24 ms（-0~33%） |
| loop | 188 ms | 166~181 ms（-4~12%） |
| sort | 15 ms | 14~16 ms |
| fib | 14 ms | 14 ms（0%） |

`fib` 是 0% 因为它几乎全是函数调用与递归，
栈顶缓存对"调用开销"没有帮助——这也印证了第 3 节的判断。

---

## 7. 建议的推进方式

1. **不要在本轮一次性做掉**。IR 重构是自举以来最大的一次结构改动，
   一次性做完风险太高。
2. 先做 22a 的第 1~3 步（生成 IR + 原样后端 + 字节一致验证），
   这一步**不改变任何输出**，纯粹是结构准备。
3. 验证通过后再做优化遍。
4. 每一步都跑 `verify_bootstrap.sh`。

---

## 8. 判断标准

如果 22a 的第 3 步（字节一致）做不到，
说明当前对语义的理解有缺口，**先修到一致**，
不要带着不一致继续往下走——这是项目一直以来的硬规则。
