# 代码生成优化（阶段四 · 起步）

状态：已实现六项优化 + 越界检查，代码体积 -30.4%（常量/数组密集程序 -41.6%）
日期：2026-10-08

## 已做的三项优化

| # | 优化 | 每条省 | 触发条件 |
|---|---|---|---|
| 1 | 常量加载窄化 `movabs rax,imm64` → `mov eax,imm32` | 5 字节 | 常量落在 0..2³²-1 |
| 2 | 局部量用 disp8 寻址 `[rbp+disp32]` → `[rbp+disp8]` | 3 字节 | 偏移落在 -128..127 |
| 3 | push 折叠 `mov rax,[rbp+o]; push rax` → `push [rbp+o]` | 1~4 字节 | 见下文 |
| 4 | 右操作数常量化 `pop rcx; add rax,rcx` → `pop rax; add rax,imm` | 3~5 字节 | 右操作数是字面量 |
| 5 | 2 的幂乘法转移位 `imul rax,rax,8` → `shl rax,3` | 2 字节 | 下标换算的步长是 2 的幂 |

## 1. 常量加载窄化

### 问题

所有整数常量加载都走 10 字节的 `movabs`：

```
48 B8 imm64          movabs rax, imm64      10 字节
```

但绝大多数常量其实很小——`0`、`1`、数组长度、字段偏移 `fi*8`、
局部/全局地址（0x401000 段、0x10000000 段）都远小于 2^32。

### 修法

`g_movabs_rax(v)` 按值域选编码：

| 值域 | 编码 | 长度 |
|---|---|---|
| `0 <= v <= 0xFFFFFFFF` | `B8 imm32`（`mov eax, imm32`，零扩展到 rax） | 5 字节 |
| 其他（负数或超 32 位） | `48 B8 imm64`（`movabs rax, imm64`） | 10 字节 |

每条省 5 字节。

### 关键约束：不能动需要回填的位置

下面这些位置的 imm64 会在 `resolve_all` 阶段被改写 8 字节，
**必须保持 10 字节编码**，所以它们不走 `g_movabs_rax`：

- `emit_call_patch`：函数调用的 `movabs rax, <函数地址>`
- `emit_startup`：启动代码里的 `movabs rax, <main 地址>`（MAINPAT）
- `g_movabs_r11`：全局变量的 `movabs r11, <地址>`

三个都在代码里**直接写字节**，不经过 `g_movabs_rax`——这是刻意的设计。

## 2. 局部量 disp8 寻址

`g_load_local` / `g_store_local` / `g_lea_local` 原先一律发 disp32：

```
48 8B 85 off32        mov rax,[rbp+off32]     7 字节
```

而绝大多数函数的帧远小于 128 字节，偏移都能塞进 disp8：

```
48 8B 45 off8         mov rax,[rbp+off8]      4 字节
```

超出 -128..127 时退回 disp32——**必须保留这条退路**，
因为编译器自身（compiler.mo）有些函数帧很大。

## 3. push 折叠

典型序列是把左操作数压栈：

```
48 8B 45 F8     mov rax,[rbp-8]
50              push rax              ; 8 → 3 字节
```

折叠成直接 push 源操作数：

```
FF 75 F8        push QWORD PTR [rbp-8]        3 字节
```

常量同理：`B8 imm32; 50`（6 字节）→ `6A imm8`（2 字节）或 `68 imm32`（5 字节）。

### 实现方式：单一清除点

难点在于「怎么知道 rax 里的值刚从哪里来」。

做法是加一个「来源标记」`K_LAST`：

- `g_movabs_rax` / `g_load_local` 在**自己发完字节之后**置标记
- **所有**其他发射都会清掉标记

清除点只需要一处：`emit1`。因为 `emit4`/`emit8` 都是建立在 `emit1` 之上的
（seed 里它们是独立的，所以在各自入口各清一次）。
任何代码生成最终都走 emit，所以标记不可能残留到不该用的地方。

`g_push_rax` 看到标记就**回退**刚发的那条指令（`K_CLEN -= n`），
再发折叠后的指令。回退长度存在 `K_LASTR` 里。

### 一个符号扩展陷阱

`push imm32` 会把 32 位立即数**符号扩展**到 64 位，
而 `mov eax, imm32` 是**零扩展**。

所以对 `v >= 2^31` 的常量，两者结果不同（`0x80000000` 会变成
`0xFFFFFFFF80000000`）。这种情况下**放弃折叠**，照旧 `push rax`。

## 实测

用 `tools/codesize.sh` 对比优化前后的代码段字节数：

| 程序 | 原始 | 现在 | 累计缩减 |
|---|---|---|---|
| 27 个测试用例合计 | 7743 B | 5390 B | **30.4%** |
| `examples/bubble_sort.mo` | 1356 B | 792 B | **41.6%** |
| 标准库测试 | 2427 B | 1603 B | **34.0%** |
| 工具链测试 | 3543 B | 2455 B | **30.7%** |
| **编译器自身** | 63919 B | 49643 B | **22.3%** |

各优化的分项贡献（冒泡排序）：

```
原始            1356
+常量窄化       1081   -20.3%
+disp8 寻址      970   -28.5%
+push 折叠       884   -34.8%
+右操作数常量化   813   -40.0%
+2 的幂移位       792   -41.6%
```

```
$ tools/codesize.sh <旧编译器>        # 逐用例对比，末尾给合计
$ tools/codesize.sh                   # 只列当前编译器的数据
```

缩减幅度取决于常量与局部变量的使用密度：
循环里塞满字面量和数组下标的程序省得最多（37%），
以函数调用为主的省得少（16%）。

### 为什么文件大小没变

第一个程序头的 `filesz` 是固定 4096（代码段被补齐到页），
数据段的文件偏移也固定在 4096。

这不是浪费：ELF 要求 `p_offset ≡ p_vaddr (mod 页大小)`，
数据段 vaddr `0x10000000` 页对齐，因此它的文件偏移必须是 4096 的倍数，
代码段只能补齐到 4096。**页对齐约束决定了文件体积下不去。**

所以这项优化的真实收益是**代码更小、指令缓存更友好**，不是文件更小。

## 2. 自举闭环是最好的回归测试

这次优化再次证明了这一点。

第一版只在 `compiler.mo`（mo 侧）改了 `g_movabs_rax`，
立刻报「自举不一致」——因为 `bin/seed` 是手写汇编，
它的 `g_movabs_rax` 还在发 10 字节。

自举要求 seed(compiler.mo) 与 moc(compiler.mo) **逐字节相同**，
所以**任何代码生成改动都必须同时改 seed 的汇编**。

第二次不一致出现在 `argc()` / `argv()` 内建：
seed 里这两个内建当初是**硬编码** `48 B8` 字节序列写的，
没走 `g_movabs_rax`，于是 seed 发 10 字节、mo 发 5 字节。

修法不是硬编码同步改一遍，而是**让 seed 的内建直接调 `g_movabs_rax`**，
从此两边共用同一份编码决策，不会再漂移。

**教训**：凡是两处都要实现的逻辑，别复制字节，要抽出单一实现点。

## 4. 右操作数常量化

最典型的一处浪费：

```
FF 75 F8        push [rbp-8]        ; 左操作数入栈
B8 01 00 00 00  mov eax,1           ; 右操作数是常量
59              pop rcx             ; rcx = 左
48 01 C8        add rax,rcx         ; rax = 右 + 左
```

右操作数明明是编译期已知的常量，却要先塞进寄存器再相加。折叠成：

```
FF 75 F8        push [rbp-8]
58              pop rax             ; 左操作数直接进 rax
48 83 C0 01     add rax,0x1         ; 左 + 常量
```

适用 `+ * & | ^`（可交换）与六个比较运算。
`- / % << >>` 不可交换，跳过。

### 比较为什么也能折叠

比较走的是 `cmp rcx, rax`，标志位语义是 **left - right**。
换成 `cmp rcx, imm` 后仍是 **left - right**，完全一致，
所以 `==` `!=` `<` `<=` `>` `>=` 六个都能折叠，不需要换寄存器。

### 实现方式：一次回退，两种 pop

`g_pop_rcx` 在发射前记下「右操作数是不是常量」，
随后的运算指令发现可以折叠时，**回退常量加载**再重发 pop：

- 可交换运算：回退后发 `58`（pop rax），再发 `op rax, imm`
- 比较：回退后发 `59`（pop rcx），再发 `cmp rcx, imm`

只改了 6 个运算函数，**解析器一行没动**——这是刻意的设计：
所有判断都收敛在代码生成层，parse 层保持无状态。

### 又踩了一次符号扩展

`and/or/xor/cmp` 的立即数形式会**符号扩展**，
而原来的 `mov eax, imm32` 是**零扩展**。
对 `v >= 2^31` 的常量两者结果不同（`0xFFFFFFFF` 一个变全 1、一个变低 32 位）。

所以统一加了上限：**只有 `v <= 2^31-1` 才折叠**，否则照旧。

### 一个 off-by-one

第一版回退时只减了常量加载的长度（`lastr`），忘了中间还夹着一条
已发射的 `pop rcx`。结果回退后指针落在 `mov eax,imm` 的**中间**，
生成了 `B8 58 48 83 C0` 这种错位的指令——20 个测试直接段错误。

修法是回退 **`lastr + 1`**，再按需重发 pop。

**是测试套件抓出来的，不是推理出来的。** 这轮再一次验证了
「先把回退长度算对」比「优化本身」更容易出错。

## 5. 2 的幂乘法转移位

数组与结构体数组的下标换算要乘上元素大小。原先一律用 `imul`：

```
48 69 C0 08 00 00 00     imul rax,rax,8        6 字节
```

而元素大小几乎总是 2 的幂（i64 数组 8、两字段结构体 16）。改用移位：

```
48 C1 E0 03              shl rax,3             4 字节
```

`g_mul_imm` 内部先判是否为 2 的幂（顺带得到 log2），是则发 shl；
步长 1 时整个指令都不发。非 2 的幂退回 `imul`。

收益集中在**大量使用数组下标**的程序：冒泡排序额外省了 2.6%，
而几乎不用下标的字符串类程序是 0。

## 6. 死跳转消除

`if` 没有 `else` 分支时会生成这样的代码：

```
0F 84 <rel32>     je els          ; 条件不成立跳到 els
<then 块>
E9 <rel32>        jmp end         ; 块结束跳过 else —— 可这里没有 else！
els:
end:
```

`els` 和 `end` 落在同一个位置，于是 `jmp end` 是**跳到下一条指令**的死跳转。

### 做法

发射 `jmp` 时记下它在跳转表里的下标、目标标签、以及结束时的 `code_len`；
`place_label` 若发现「目标正是这里」且「中间没夹任何字节」，就把 `code_len`
回退 5 字节，并把跳转表长度减 1。

判断「中间没夹字节」靠 `emit1` 清标记——**所有字节发射的唯一出口**，
这一点前面几项优化已经依赖过，这里再次复用。

### 踩坑：删字节会让已放置的标签失效

第一版上线后测试直接卡死（有个程序陷入死循环）。

原因：`els` 比 `end` **先**放置，落在被删掉的 5 字节之后。
删掉 jmp 后 `els` 仍指向老位置——而那里现在是下一段指令的中间，
`je els` 于是跳进了别的指令中间。

修法：回退之后，**把所有值等于老位置的标签一并回退**：

```mo
while i < nn {
    if load64(heap + O_LB + i * 8) == old {
        store64(heap + O_LB + i * 8, nw);
    }
    i = i + 1;
}
```

教训很直白：**删除已发射的字节，必须回头修正所有指向它的引用。**
跳转表减一项容易想到，标签表却容易漏——因为标签是"先放的那个"，
从删除点看过去是"过去的事"。

### 收益

| 程序 | 无优化 | 有优化 | 缩减 |
|---|---|---|---|
| `wc.mo` | 4815 | 4710 | 2.2% |
| `grep.mo` | 5054 | 4944 | 2.2% |
| `sort.mo` | 5198 | 5103 | 1.8% |
| **编译器自身** | 54237 | 53052 | **2.2%** |

比前几项温和，因为每个 `if` 只省 5 字节，而非 `if` 密集的程序收益就小
（`bubble_sort` 只有 0.6%）。

## 7. 新增诊断：缺少 return

原先函数末尾没有 `return` 会**静默返回垃圾值**（rax 里残留什么就是什么）。
现在会拦下：

```
test.mo:2:4: error: missing return statement in a function returning i64
fn g(a: i64, b: i64) -> i64 {
   ^
```

### 只做保守检查

当前实现只判断「函数体里**出现过** `return` 」，**不做全路径分析**。
所以下面这段是合法的（虽然有一条路径没有 return）：

```mo
fn pick(c: i64) -> i64 {
    if c > 0 { return 7; }
    return 0;          # 有这一句就放行
}
```

而这样会被拦下：

```mo
fn pick(c: i64) -> i64 {
    if c > 0 { return 7; }
}                      # 完全没有 return -> 报错
```

全路径分析需要控制流图，留待后面做。
保守检查已经能抓住绝大多数真实笔误（漏写 return）。

### 一处刻意的非对称

**这个检查只在 `moc` 里，没有镜像到 `bin/seed`。**

理由：`seed` 是引导编译器，唯一职责是把 `compiler.mo` 编出来。
它连语法都只支持一个子集，诊断也只有一句 `error: syntax error`（无行列号）。
为了一个它永远不会触发的检查去写几十行汇编，收益为零。

这与「代码生成必须两边一致」不冲突：
**影响输出字节的改动必须镜像，只影响诊断的不必。**
判断标准很直接——`verify_bootstrap.sh` 只比字节，不比诊断。

## 8. 还没做的优化

按性价比排序，都留待后续：

| 优化 | 预估收益 | 难点 |
|---|---|---|
| 左操作数常量化（`1 + x` 里 1 那侧） | 每处 3 字节 | push 已在右操作数代码之前发射，无法事后回退；需延迟发射 |
| 常量折叠（编译期算 `2*3`） | 依程序而定 | 同上：代码是边解析边发射的，折叠需要延迟或重排 |
| 比较/算术直接用 rcx，省 push/pop | 每处 2-3 字节 | 需要引入寄存器分配 |
| `jcc` 到紧接着的标签（条件分支版本） | 每处 6 字节 | 同上的引用修正问题，收益面更窄 |
| 全局量 `movabs r11,addr; mov rax,[r11]` → 直连 | 每处 2 字节 | 地址与代码相距超 2GB，无法用 RIP 相对寻址，收益有限 |
| 跳转优化（`jmp` 到下一条指令删掉） | 每处 5 字节 | 需要基本块信息 |

### 为什么常量折叠一直没做

代码是**边解析边发射**的，没有 AST。要折叠 `2*3`，
必须在发射之前就知道两边都是常量——但左操作数的字节已经发出去了。

前面几项优化能成立，是因为它们要么只动**最后一条指令**（右操作数常量化、
push 折叠），要么只改**单条指令的编码**（常量窄化、disp8、移位）。
全都避开了「回退跨越已发射代码」这个难题。

真正的常量折叠需要引入一层中间表示（或至少延迟发射），
那是阶段四之后的重构，不是补丁能解决的。

### 前提

影响**输出字节**的优化必须在 seed 的汇编里同步实现，否则自举立刻报警。
这也是为什么墨语言的优化推进偏保守——**正确性由自举兜底，代价是改两遍。**
