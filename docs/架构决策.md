# 架构决策记录

## 为什么包格式自己写

用现成格式（deb/rpm/apk）等于变成别人的衍生版，且后期无法自由演进。
三段式（header / meta / data + 可分离 sig）让验签、元数据查询、换压缩算法
三者互不干扰。

## 为什么配方用 Python 而不是 shell DSL

shell DSL（APKBUILD / PKGBUILD）需要自己实现解析、变量展开和静态检查。
Python 模块直接复用语言本身，配方的条件逻辑、子包拆分、版本变换都能写清楚，
单人维护成本最低。代价是配方可以执行任意代码——靠沙箱和断网兜底。

## 为什么构建隔离分两级

* 环境净化（默认）：统一 PATH、编译参数，清空宿主侵入变量。
* 命名空间（root 下自动）：mount/pid/user 命名空间 + 默认断网。
* 完整 chroot 到自建 rootfs 是第三级，**自举之后才用得上**，接口先留着。

在自举之前就用 chroot，等于先有鸡后有蛋。

## 为什么构建依赖装进 sysroot 而不是宿主

* 宿主被污染后，构建结果混入宿主差异，可复现性无法保证。
* sysroot 与 host 分离，正是交叉编译的标准结构。今天装的是同架构包，
  明天换成交叉工具链，只需换 sysroot 的指向。

## 为什么包管理器用 Python + SQLite

包管理器是最怕出错的组件。Python 没有内存安全问题，SQLite 提供索引能力
（查文件归属、反查依赖者、孤儿包判断），包数上千后纯文本记录会明显变慢且易损坏。

## 已知取舍

* 系统级原子升级与回滚（快照/双分区）尚未实现，目前是文件级回滚日志。
* 只支持 x86_64，指令集基线未做分级。
* 包内安装脚本（pre/post install）字段已定义，执行器未接。
